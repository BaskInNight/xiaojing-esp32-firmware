# 小净 Arduino 固件代码梳理报告（ESP-IDF 重构前）

> 审计日期：2026-07-21  
> 审计对象：当前仓库中参与 PlatformIO 编译的 ESP32-S3 Arduino 固件  
> 审计深度：架构、关键状态机、关键数据流、接口与安全边界；未逐行复述诊断代码、字体数组、提示音 Base64 和 Edge Impulse 生成代码  
> 用途：作为下一轮确认新功能、新外设和 ESP-IDF 架构的现状基线，不作为新版本需求说明书

## 1. 结论摘要

当前工程是一套已经能编译、能覆盖比赛演示主链路的 Arduino Demo 固件，核心能力包括：

- ESP32-S3 双核运行，Core 1 承担 Arduino 主循环，Core 0 按需执行云端 AI 请求。
- 外筒步进电机在 0°、90°、180° 三个 IPS 位置之间切换。
- BLDC 电机完成波轮正反转、滚筒单向洗和高速脱水。
- 支持进水、水位检测、浊度检测、UV 灯、EC11、PAJ7620 手势、TFT/LVGL 显示。
- 支持三种启动来源：本地按键/手势 Demo、BLE 小程序、语音 AI。
- 支持本地唤醒、VAD 录音、MiMo Tool Calling、TTS、本地提示音、Wi-Fi 和 ArduinoOTA 服务。

但它不适合逐文件翻译为 ESP-IDF。当前代码同时混合了业务逻辑、硬件时序、云端协议、UI、诊断开关和比赛 Demo 流程，而且“文档描述的安全架构”与“当前源码真正执行的安全架构”存在明显差异。

重构时建议保留的是已经实机调过的物理参数和动作经验，例如 BLDC 启动曲线、IPS 极性与消抖、步进方向、VAD 参数、引脚分配；需要重做的是任务模型、消息协议、安全仲裁、错误状态、资源所有权和完整洗涤业务流程。

## 3. 当前总体架构

```text
                    ┌──────────────────────────────┐
本地按键 / 手势 ───►│                              │
BLE JSON ──────────►│  main.cpp：入口与流程拼装    │
语音 / 云端 AI ────►│                              │
                    └──────────────┬───────────────┘
                                   │ WashStep_t
                                   ▼
                    ┌──────────────────────────────┐
                    │ WashExecutor：单步队列/状态机 │
                    └──────────────┬───────────────┘
                                   │ 驱动调用
                                   ▼
                    ┌──────────────────────────────┐
                    │ HardwareDriver：GPIO/总线/电机│
                    └──────────────────────────────┘

旁路子系统：
- DisplayDriver 从执行器和驱动层拉取状态，再更新三页 UI。
- BLEDriver 在回调中收包，在 main loop 中取出完整 JSON。
- CloudTask 在 Core 0 处理 WAV/Base64/HTTPS/JSON，并通过全局共享变量把结果交回 Core 1。
```

分层意图是清楚的，但边界目前没有完全守住：

- `main.cpp` 直接读写 MCP23017、I2S、任务看门狗和执行器队列。
- `DisplayDriver` 直接访问执行器和传感器，而不是消费统一状态快照。
- `WashExecutor` 既负责状态机，又内置了浊度重洗业务流程。
- AI、安全补全、BLE Demo 和离线 Demo 各自拼接队列，规则不统一。
- 硬件资源没有唯一所有者，尤其是 I²C/MCP23017。

## 4. 启动流程

`setup()` 的实际顺序如下：

1. 安装 GPIO ISR 服务，启动串口，并阻塞等待 1 秒。
2. 初始化 I2S_NUM_0，同时启用 RX 和 TX，默认 16 kHz、32 bit、双声道帧。
3. `EXE_Init()` 初始化硬件驱动，并自动排队：
   - 外筒回 0°；
   - BLDC 内筒寻零。
4. 启动 I²C 100 kHz，直接配置 MCP23017 方向寄存器，并关闭功放。
5. 初始化 PAJ7620、TFT 和 LVGL。
6. 同步等待 Wi-Fi，最多约 10 秒。
7. 初始化 NimBLE。
8. Wi-Fi 成功时启动 ArduinoOTA；失败时继续保留 BLE 本地能力。

启动完成后，最先由执行器执行的是外筒归零和 BLDC 归位。由于语音唤醒在 `EXE_IsWashing()` 为真时被禁止，正常情况下要等这两步结束才进入语音待命。

## 5. 主循环调度顺序

`loop()` 每轮依次处理：

1. ArduinoOTA。
2. `EXE_Handler()` 洗涤动作状态机。
3. FastAccelStepper 管理。
4. MCP23017 心跳 LED。
5. 每秒一次 BLE 状态/进度通知。
6. BLE JSON 命令解析和队列拼装。
7. EC11/手势启动、停止和翻页。
8. 每 10 秒检查 Wi-Fi 重连。
9. 每 200 ms 更新显示数据，并持续调用 LVGL handler。
10. 读取 EC11 旋钮。
11. 执行语音状态机：唤醒检测或录音/云端流程。

洗涤动作状态机本身主要基于 `millis()`，但整个主循环并非严格非阻塞：录音使用内部 `while` 循环，音频播放使用阻塞式 I2S 写入，TTS 使用同步 HTTP，运行路径中也仍有多处 `delay()`。

## 6. 三条控制入口

### 6.1 本地离线 Demo

待机时，EC11 按键或 PAJ7620 上挥会启动固定比赛流程：

```text
外筒 0° → BLDC 归位 → 进水+UV 3s → 波轮洗 9s
→ 外筒 90° → 滚筒洗 5s → 外筒 180° → 脱水 8s → 外筒 0°
```

洗涤中，EC11 按键或下挥会调用 `EXE_ClearQueue()`，立即关闭水阀和 UV、刹停 BLDC、停止步进电机。

此流程是演示序列，不是完整洗衣业务：没有排水、漂洗、门锁等动作。

### 6.2 BLE 小程序

当前 BLE GATT：

| 项目 | 值 |
|---|---|
| 设备名 | `JJTP-XIAOJING` |
| Service | `FFF0` 128-bit 标准扩展形式 |
| Write | `FFF1`，WRITE + WRITE_NR |
| Notify | `FFF2`，NOTIFY + READ |

手机发送最多 512 字节的 JSON。固件通过大括号深度判断分片是否完整，然后由主循环处理：

- `{"cmd":"start", ...}`：清空队列，加入归零、进水、可选波轮洗、固定滚筒洗、可选脱水、浊度检测和归零。
- `{"cmd":"stop"}`：清空队列并停机。

设备通知目前有三类紧凑文本：

- `P,<progress>`：进度；当前实际只发送洗涤中 50、空闲 0。
- `S,<code>`：washing、busy、done、idle 等状态。
- `A,<phase>,<seq>`：语音/云端阶段。

BLE 控制链路目前存在两个需要后续重新定义的点：

- `dry.time` 在入队前被除以 60，而执行器把 `time` 当秒使用，单位明显不统一；例如输入 20 会变成 0 秒。
- BLE JSON 结构与仓库文档示例不完全一致，IDF 开发前必须以新版小程序协议重新冻结字段、单位、范围和版本号。

### 6.3 语音 AI

实际链路如下：

```text
INMP441
  → Edge Impulse 滑窗唤醒（xiao_jing > 0.8）
  → 本地唤醒提示音
  → 最长 5s 的 VAD 录音
  → WAV + Base64
  → Core 0 HTTPS 请求 MiMo mimo-v2.5
  → Tool Calling: speech_reply / updated_preferences / pipeline[]
  → 恢复 BLE
  → 云端 TTS mimo-v2.5-tts
  → TTS 播完后把 pipeline 推入 WashExecutor
```

关键参数：

| 项目 | 当前值 |
|---|---|
| 唤醒阈值 | `xiao_jing > 0.8` |
| 录音格式 | 16 kHz / 16 bit / mono |
| 最大录音 | 5 秒，约 160 KB PCM |
| 前置静音窗口 | 400 ms |
| VAD 能量阈值 | 600，音频在高通后放大 8 倍 |
| 有效语音后静音截断 | 1.2 秒 |
| 空唤醒退出 | 2.5 秒 |
| 对话模型 | `mimo-v2.5` |
| TTS | `mimo-v2.5-tts`，声音“冰糖” |
| 偏好存储 | NVS namespace `xiaojing`，key `user_pref` |

Core 0 云任务是每次录音后临时创建、自删除，不是常驻任务池。Core 1 在等待期间仍循环调用执行器、步进管理、心跳和显示。

为缓解 BLE/Wi-Fi/TLS 内存和射频问题，现代码在云请求前完整反初始化 NimBLE，请求后再重新初始化。这个机制属于 Arduino Demo 的资源规避方案，不应直接成为 IDF 新架构的默认方案。

## 7. `WashStep_t` 协议与执行器实际行为

消息结构为：

```c
typedef struct {
    WashCmd_t cmd_id;
    uint16_t val;
    uint16_t time;
} WashStep_t;
```

当前队列上限 20 条，使用 `std::queue`，由一个 FreeRTOS mutex 保护主要入队/出队操作。

| 指令 | 当前执行行为 | 完成条件/额外动作 | 现状备注 |
|---|---|---|---|
| `CMD_WATER_IN` | 开进水阀，`val=1` 时开 UV | 水满且超过 500 ms，或固定 30 s 超时 | `time` 参数实际被忽略；步骤结束时只关水阀，不主动关 UV |
| `CMD_WASH_PULSATOR` | 9 s 周期正反转：25% 软启动、目标转速、制动预置方向 | `time` 秒后再强制刹车 3 s | val 1/2/3 对应 35/50/65%；没有姿态校验 |
| `CMD_TILT_BARREL` | 按目标 IPS 连续驱动步进 | 到达 IPS，或 0° 80 s、其他位置 40 s 超时 | 与头文件 `MAX_TILT_SEC=7` 不一致 |
| `CMD_WASH_DRUM` | 正转，前 3 s 分段升速 | `time` 秒后刹车 3 s | val=1 为 25%，其他值均为 40%；没有 90° 校验 |
| `CMD_SPIN_DRY` | 正转，前 5 s 分段升速 | `time` 秒后刹车 5 s | val=1 为 40%，其他值均为 85%；没有 180° 校验，也没有使用 120 s 上限 |
| `CMD_HOME_BLDC` | 先 25%，后 15% 正转寻找 BLDC IPS | 触发后刹车 2 s；15 s 未触发则本步结束 | 超时不会清空后续洗涤队列 |
| `CMD_TURBIDITY_CHECK` | 读取 10 次 ADC 均值并换算 NTU | 超过 800 NTU 或 `val=1` 时追加固定重洗序列 | `val=1` 在协议中写的是“持续监测”，实现却解释为“强制重洗” |
| `CMD_UV_STERILIZE` | `val=1` 开 UV，持续 `time` 秒；0 秒默认 60 秒 | 时间结束关 UV | 仅在 `elapsed_ms == 0` 时执行开灯，存在首次调度不恰好为 0 时漏开的可能 |

队列为空时，执行器会一次性确保水阀和 UV 关闭，并持续给 BLDC 发送 0% PWM。

## 8. BLDC、步进与传感器细节

### 8.1 BLDC

- GPIO 39 输出 LEDC ch0，20 kHz、8 bit；GPIO 42 控制方向。
- `brake()` 的实际含义是 PWM=0，不是独立硬件制动信号。
- 波轮洗 9 秒循环：
  - 0–1.0 s：CW 25%；
  - 1.0–3.0 s：CW 目标速度；
  - 3.0–4.5 s：PWM 0 并预置 CCW；
  - 4.5–5.5 s：CCW 25%；
  - 5.5–7.5 s：CCW 目标速度；
  - 7.5–9.0 s：PWM 0 并预置 CW。
- 这组时序与旧文档中的 0.7/2.5/1.0 秒分段不同，应以当前源码和实机验证结果为准。

### 8.2 外筒步进

- PUL=41、DIR=40、ENA=48，ENA 常态 LOW。
- FastAccelStepper 速度 4000 Hz，加速度 2500。
- 不按步数闭环，而是连续转动直到对应 IPS 触发。
- `realPosture` 只在 IPS 确认后更新；启动时为 UNKNOWN。
- 0° 使用一个方向，90°/180° 根据目标枚举与已知姿态决定方向。

### 8.3 IPS 与其他传感器

- 四个 IPS 均为 LOW 触发、内部上拉。
- 单点读取要求连续稳定：0°/90°/BLDC 为约 3 ms，180° 为约 20 ms。
- 水位为 GPIO 4 HIGH=满。
- 浊度为 GPIO 5 ADC，10 次采样平均，当前公式为 `NTU = max(0, -865.68 * voltage + 3291.3)`，尚未看到温度补偿和多点标定。
- PAJ7620 ISR 只置位，I²C 读取在主循环完成，这个中断结构可以保留。
- EC11 使用 ESP32Encoder 全四倍频，并用软件累计/滞回抑制正数区间跳动。

## 9. 显示、网络和 OTA

### 9.1 显示

ILI9341 横屏 320×240，LVGL 8.3，单缓冲大小为 320×12 行。三页分别是：

1. 系统状态：BLE、Wi-Fi、洗涤状态、姿态、水位、浊度和 IPS。
2. 洗涤进度：进度条、当前步骤、姿态和后续队列预览。
3. 语音助手：等待、唤醒、倾听、思考、回复和结束动画。

当前显示的洗涤进度只是 0%/50%，不是真实总进度；页面虽然已有队列预览，但尚未形成统一的状态数据模型。

### 9.2 网络与 OTA

- Wi-Fi 在启动阶段最多同步等待 10 秒，之后每 10 秒尝试重连。
- HTTPS 使用 `setInsecure()`，不校验证书。
- LLM 请求手动构造 HTTP/1.1，只支持非 chunked 响应，响应体最大 32 KB。
- TTS 使用 Arduino `HTTPClient`，响应缓冲上限 500 KB。
- ArduinoOTA 仅在启动时 Wi-Fi 已连接成功的情况下初始化；如果启动时失败、后续重连成功，代码不会补做 OTA 初始化。

## 10. 文档与源码不一致项

以下结论以 2026-07-21 当前源码为准：

| 旧文档/注释说法 | 当前源码实际情况 |
|---|---|
| AI 的 `CMD_TILT_BARREL` 会被忽略 | AI 的 `CMD_TILT_BARREL` 会被接受；只忽略 `CMD_HOME_BLDC` |
| 队列起始自动注入 `TILT(0)+HOME_BLDC` | AI 路径只固定前置 `HOME_BLDC`；BLE/离线路径各自手工加入 `TILT(0)+HOME` |
| 滚筒洗和脱水前由系统自动补姿态 | 执行器没有自动补全，也没有姿态前置校验，主要依赖 AI 提示词或调用方正确拼队列 |
| 队尾自动追加浊度检测和归零 | AI 路径只保证归零，并默认插入 UV；不自动追加浊度检测 |
| Web 服务在 Core 0 常驻 | `WebInterface.cpp` 已排除编译 |
| 云任务是静态常驻任务池 | 每次语音请求按需创建，完成后自删除 |
| `MAX_TILT_SEC=7` 是换筒硬上限 | 执行器实际使用 40/80 秒 |
| `pio run -t upload` 自动选择 OTA | 当前上传协议固定为 esptool |
| 波轮 softstart 为 0.7/2.5/1.0 秒分段 | 当前实际为 1.0/2.0/1.5 秒对应分段 |

## 11. 当前安全边界与主要技术债

这里不是逐项要求马上修补 Arduino 代码，而是标出 IDF 需求设计时不能沿用的假设。

### 11.1 必须优先重新设计的安全问题

1. **执行器缺少硬姿态联锁。** `WashExecutor.cpp` 注释明确写着“已移除安全前置拦截”，因此波轮、滚筒和脱水可在错误姿态直接启动。
2. **AI 仍能决定姿态指令。** 当前只屏蔽 AI 的 BLDC 归位，不屏蔽换筒；安全主要依赖提示词，不属于本地强制安全。
3. **输入参数没有统一校验。** `val`、`time`、角度、队列顺序和最大时长没有在单一入口规范化，头文件中的多数上限没有被使用。
4. **BLDC 寻零失败后仍可能继续后续队列。** 15 秒超时只结束当前步骤，没有进入故障锁定或清队列。
5. **没有独立故障态。** 当前主要是“打印错误、结束本步或清队列”，缺少可查询、可复位、禁止再次启动的 FAULT 状态和错误码。
6. **现有硬件没有排水和门锁控制。** 因而无法实现完整的进水—洗涤—排水—漂洗—脱水安全闭环。

### 11.2 并发与资源所有权问题

1. Core 0 与 Core 1 之间大量使用 `volatile` 全局变量交换 AI 状态、PCM 指针、TTS 指针和 pipeline，缺少完整的生命周期与内存所有权协议。
2. 主核 120 秒等待超时后只把 `cloud_task_done` 强制设为 true，并没有停止仍可能运行的 CloudTask；旧任务可能继续写共享状态。
3. MCP23017 通过多个“读寄存器—修改—写回”函数访问，没有 I²C mutex 或统一输出 shadow register。Core 0 控制功放时，Core 1 仍可能更新心跳或其他 MCP 输出，存在竞态和位丢失风险。
4. BLE 收包回调和主循环共享 512 字节缓冲，仅用 `volatile bool` 表示一条待处理命令，没有锁/队列；大括号计数也没有处理 JSON 字符串中的花括号。
5. WashExecutor 的 mutex 主要保护队列，但部分活动状态和当前步骤读取仍在锁外，不是完整的并发状态模型。

### 11.3 阻塞与实时性问题

1. 活跃路径中仍有 `delay()`，包括 BLE 初始化、云请求前后和 TLS 前处理。
2. IPS 消抖通过循环等待 1 ms tick，180° 一次读取可占用约 20 ms。
3. VAD 录音在主循环内运行长 `while`，虽然人工调用了执行器和 UI handler，但结构难以保证所有高优先级安全检查的最坏响应时间。
4. TTS HTTP、Base64 解码和 I2S 播放为同步流程。
5. 云任务临时删除 Core 0 idle task 的任务看门狗订阅，说明现有任务时序尚未形成可靠的 watchdog 策略。

### 11.4 业务语义问题

1. 进水命令的 `time` 名义上是最大等待秒数，实现固定使用 30 秒。
2. 进水开启 UV 后，本步骤完成不会关 UV，UV 会延续到后续步骤或最终空闲清理。
3. 浊度命令的 `val` 定义和实现语义不一致。
4. 浊度超标会硬编码追加重洗流程，但没有排水动作，也没有重洗次数上限。
5. BLE 脱水时间存在秒/分钟换算问题。
6. AI JSON 解析的部分失败路径仍可能被标记为结果就绪；若内存分配或中间构建失败，也有错误码未完整落地的路径。
7. 队列满时只丢弃新指令并打印，调用方无法得知一个“完整程序”已经被截断。

## 12. 当前硬件能力边界

|---|---|

### 12.2 当前代码中没有

- 门盖检测、电磁锁及锁状态反馈。
- 洗涤剂/柔顺剂投放泵。
- 加热器与温度传感器。
- 风机、烘干或湿度传感器。

## 13. ESP-IDF 重构建议边界

在新功能和新外设尚未确认前，不建议立即开始写 IDF 业务代码。更合适的顺序是：

1. 冻结整机物理流程：每个洗涤阶段的进水、排水、姿态、门锁、转速、UV、检测与异常恢复。
2. 冻结新硬件清单和最终引脚/总线表，确认高低有效、电源域、反馈信号和默认安全电平。
3. 定义本地安全状态机，确保 BLE、AI、UI 只能提交“意图/程序”，不能直接越过安全仲裁控制执行器。
4. 定义版本化命令协议、参数单位、范围、应答、取消、暂停、故障和恢复语义。
5. 再确定 IDF component 和 FreeRTOS task 的划分，以及每个外设的唯一 owner。

建议的 IDF 逻辑层次是：

```text
输入适配层（BLE / Voice / Local UI）
              │ 只提交请求
              ▼
程序规划与参数校验层
              │ 已规范化 WashProgram
              ▼
本地安全仲裁 + 整机状态机
              │ 受联锁保护的原子动作
              ▼
设备服务层（motor / barrel / water / lock / uv / sensors / audio）
              │
              ▼
ESP-IDF 驱动层（GPIO / LEDC / GPTimer/RMT/MCPWM / I2C / ADC / I2S / SPI）
```

建议保留/迁移的“知识”而不是 Arduino API：

- BLDC 软启动、换向、刹车等待和不同姿态负载下的速度曲线。
- 步进方向约定、4000 Hz/2500 加速度的实机参数、IPS 极性和 180° 的特殊抗噪经验。
- 水位与浊度的当前采样方式，作为后续重新标定的起点。
- 唤醒阈值、VAD 阈值和本地提示音交互节奏。
- BLE UUID 和小程序兼容需求；具体 payload 应重新版本化。

不建议直接照搬：

- Arduino `loop()` 的人工轮询顺序。
- `std::queue` + 多个共享全局变量的通信方式。
- 由 AI prompt 保证安全顺序的方案。
- MCP23017 分散式 RMW。
- 同一 I2S 端口的临时格式切换逻辑，除非新硬件确认仍只能共享。
- 为 TLS 临时反初始化 BLE、删除 idle watchdog 的规避逻辑。

## 14. 下一轮需要确认的信息

为了把现状报告转为 IDF 的正式需求与架构，下一轮建议按下面五组信息沟通：

1. **新整机流程**：从关机/待机到洗完归位，每一步动作、判断、超时、允许跳过项和失败处理。
2. **新外设表**：新增、删除、替换的器件；接口类型；引脚；高低有效；是否有反馈；上电默认状态。
3. **控制入口**：本地旋钮/按键、手势、BLE、小程序、语音 AI、OTA 各自保留到什么程度，优先级如何。
4. **安全约束**：门锁、姿态、进排水、电机、UV、急停、断电恢复和故障复位规则。
5. **产品化目标**：仍是比赛 Demo，还是需要长期运行、断电续洗、日志、量产配置、安全升级和版本兼容。

本报告的结论可以作为“旧系统现状”，下一轮的新描述应单独形成“IDF 版功能需求与状态机”，不要直接在旧流程上打补丁。
